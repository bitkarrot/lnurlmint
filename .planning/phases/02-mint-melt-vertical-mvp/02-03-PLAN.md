## Phase Goal

**As a** note holder, **I want to** check my note's value via the informational `/w` endpoint and melt it back to sats via the withdraw callback, **so that** I can redeem my bearer note through any spec-compliant LNURL-withdraw wallet.

## Acceptance Criteria

- [ ] `GET /lnurlmint/w/{mint_id}?k1=...` returns a LUD-03 `LnurlWithdrawResponse` with `callback`, `k1` (echoed verbatim), `minWithdrawable = maxWithdrawable = note.amount_msat`, `defaultDescription`.
- [ ] `/w` is purely informational — it never calls `mark_pending`, `finalize_melt`, or `restore`.
- [ ] `/w` rejects pending notes with `{"status":"ERROR","reason":"pending"}` (SEC-04).
- [ ] `/w` rejects unknown notes with `{"status":"ERROR","reason":"Unknown note."}`.
- [ ] `/w` rejects spent notes with `{"status":"ERROR","reason":"Note already spent."}`.
- [ ] `/w` lazily materializes the note via `_try_settle_mint` if it's not yet in the DB but the mint invoice has settled.
- [ ] `/w` ignores the `amount` query param (unauthoritative — `maxWithdrawable` is).
- [ ] `GET /lnurlmint/w/cb/{mint_id}?k1=...&pr=...` implements melt: validates the invoice, rejects duplicate/self-mint payment hashes, calls `mark_pending` atomically, replies `{"status":"OK"}` immediately, schedules background `_melt_pay`.
- [ ] `pr` MUST NOT combine with multiple `k1`s or `amount` — returns `{"status":"ERROR","reason":"pr cannot be combined with multiple k1s or amount - merge or split first."}` (REDEEM-06).
- [ ] `h` is required when `pr` is absent — returns `{"status":"ERROR","reason":"missing h"}` (REDEEM-06). Phase 3 implements rotate/split/merge; Phase 2 returns "missing h" or defers.
- [ ] Self-mint rejection: if the pr's payment_hash exists in `mints_records`, returns `{"status":"ERROR","reason":"Cannot melt into an invoice this mint issued itself."}` (SEC-06).
- [ ] Duplicate-melt rejection: if the pr's payment_hash exists in `melts`, returns `{"status":"ERROR","reason":"Invoice already used by an earlier melt - use a fresh one."}` (SEC-06).
- [ ] `mark_pending` raises `PendingNoteError` → returns `{"status":"ERROR","reason":"pending"}`.
- [ ] `_track_melt_start` is called after `mark_pending` succeeds and BEFORE the background task is scheduled (SEC-03).
- [ ] No query string with `k1` or secret is logged on `/w` or `/w/cb` (SEC-05).

## Artifacts This Phase Produces

This plan delivers the redeem side of lnurlcash: the informational LUD-03 withdrawRequest (`/w`) that advertises a note's value without burning it, and the mutating melt callback (`/w/cb`) that reserves the note, responds OK immediately, and schedules the background payment. The `/w` endpoint also triggers lazy settlement — if the note isn't materialized yet but the mint invoice has settled, `_try_settle_mint` materializes it on the first poll. The melt callback validates the invoice (rejecting self-mint and duplicate-melt payment hashes), atomically marks the note pending, and schedules `_melt_pay` (implemented in Plan 04).

Deliver the informational withdrawRequest (`/w`) and the mutating melt callback (`/w/cb`). The `/w/cb` melt callback validates the invoice, atomically reserves the note, responds OK immediately, and schedules the background `_melt_pay` task (Plan 04).

Purpose: The redeem flow is the other half of lnurlcash. A holder presents their k1 to `/w` to see the note's value, then submits a pr to `/w/cb` to melt it back to sats. The confirm-before-burn state machine (Plan 04) ensures the note is only burned on positive settlement. The melt callback responds immediately (LUD-03 compliance) and pays asynchronously.
Output: Two new endpoints in views_lnurl.py, updated crud.py if needed.
