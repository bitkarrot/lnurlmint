## Phase Goal

**As an** LNbits wallet owner, **I want to** create a per-wallet mint via the management API and see it displayed on the extension's page, **so that** the full extension stack (loader, migration, DB, API, UI) is proven working before any LNURL or Lightning functionality is added.

## Acceptance Criteria

- [ ] LNbits loads the lnurlmint extension without errors; it appears in the extensions list with valid metadata.
- [ ] The m001_initial migration creates the `lnurlmint.mints` table with all columns from DATA-01 on SQLite.
- [ ] `POST /lnurlmint/api/v1/mints` with an admin key creates a mint row and returns the `Mint` object.
- [ ] `GET /lnurlmint/api/v1/mints` with an invoice key returns a list of mints scoped to the authenticated wallet.
- [ ] The placeholder Vue page at `/lnurlmint/` fetches and displays the mint list.
- [ ] No new Python dependencies are added beyond LNbits' `pyproject.toml`.
- [ ] All pydantic models use v1 syntax (`BaseModel`, `validator`, `root_validator`, `class Config`).

## Artifacts This Phase Produces

This plan produces the walking skeleton of the lnurlmint extension: a working end-to-end create-and-list mint flow with the extension bootstrap, database schema (mints table), pydantic v1 models, wallet-scoped CRUD, management API endpoints, and a placeholder Vue page. The remaining three tables (notes, mints_records, melts), full CRUD (get/update/delete), and cross-wallet isolation tests are deferred to Plans 02 and 03.

<threat_model>
ASVS Level: 1 | Blocking Threshold: high

| Threat | Severity | Mitigation |
|--------|----------|------------|
| Cross-wallet data leakage via management API | high | Every query scoped by `WHERE wallet = :wallet` using `wallet.wallet.id` from `require_admin_key`/`require_invoice_key` decorator; wallet_id never taken from request body |
| Supply chain risk from new dependencies | medium | EXT-04: audit all imports against LNbits `pyproject.toml`; only `coincurve` (transitive, already used by LNbits core) is used for keypair generation |
| Input validation bypass on mint creation | medium | `CreateMint` pydantic v1 model with `Field(ge=0)` constraints and `root_validator` for bounds checking; invalid input rejected at model validation layer |
</threat_model>
